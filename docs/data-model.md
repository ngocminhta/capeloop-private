# Data model

This page documents the concrete v1 Python serializers, generated JSON
Schemas, and runner artifacts in this repository. It is a description of the
implemented contract, not a proposed future format.

There are three related but distinct layers:

1. Immutable Python records in `cape_loop.schemas`, `cape_loop.beliefs`, and
   `cape_loop.native`.
2. The release-facing schemas generated by `cape_loop.schema_export`.
3. Experiment-specific JSON and JSONL rows written by `cape_loop.runner`.

Do not assume that every Python `to_dict()` result is independently versioned
or that every experiment row has a generated schema. The exact boundaries are
listed below.

## Dataset identity and scope

| Dataset field | Value |
| --- | --- |
| Name | CAPE-Loop Synthetic Interaction Benchmark |
| Source | Repository simulator plus a frozen model-assisted conversation-surface input |
| Release status | Generator, configurations, and schemas are available; no paper-frozen empirical dataset is checked in |
| DOI/archive identifier | Not assigned |

CAPE-Loop does not download or repackage an existing benchmark. A dataset is a
checksum-verified run generated from one resolved TOML configuration, source
digest, master seed, and semantic object identifiers. It is not one static
table bundled with the repository.

Four layers must remain separate:

| Layer | Producer | Canonical storage | Meaning |
| --- | --- | --- | --- |
| Synthetic interaction data | CAPE-Loop population, policy, response-model, and updater code | Verified `runs/<run-id>/`; JSON/JSONL with derived CSV tables | Controlled experimental world and simulator observations |
| Frozen conversation surfaces | Outcome-blind project standardization assigns three source-neutral frame families and neutral name pools; code expands fixed treatments/reply | `data/scenarios/conversation-templates-v1.json`; copied to `inputs/conversation-templates.json` in each consuming run | Natural-language realization of already-fixed choices, not a decision source |
| External model data | Explicit OpenAI/OpenRouter collection or validated replay; optional direct decoder replications are separate | `llm/` in a completed run or a separately checksummed collection | External observations that are replayable but not regenerable |
| Human data | Separately authorized participant study | De-identified imported JSONL plus protected codebook/protocol records | Deferred pragmatic validation |

Repository code creates latent users, options, presentation contexts,
mathematical choices, and reference updates. An LLM may draft candidate neutral
wording and display names in a separate OpenRouter workflow, but it receives no
latent user, never selects an option, and never writes treatment sentences or
user choices. The current visible bases were subsequently standardized by the
project onto three source-neutral frame families. Runtime code expands and
renders those frozen inputs.

The generated latent preference has three coordinates:

```text
theta_j in {-2, -1, +1, +2}
```

Each user also has ranking, default, and suggestion susceptibility. Preference
and susceptibility remain fixed within a trajectory. Travel and writing each
use three controlled attributes. Scenario semantics are project-authored
fixtures, and their current frozen conversation surfaces are
project-standardized language rather than scraped conversations. Historical
model-assisted candidate authoring remains recorded separately.

The default response family is finite random utility. Presentation changes the
probability of a response but never changes latent preference or intrinsic
welfare. A separate rule-based family is available for sensitivity analysis.
These are declared experimental instruments, not fitted models of human
behavior.

## Production and storage

The canonical offline production sequence is:

```bash
PYTHONPATH=src python -m cape_loop run configs/offline/experiment_a.toml
PYTHONPATH=src python -m cape_loop run configs/offline/experiment_b.toml
PYTHONPATH=src python -m cape_loop run configs/offline/experiment_c.toml
PYTHONPATH=src python -m cape_loop run configs/offline/experiment_c_seed_271828.toml
PYTHONPATH=src python -m cape_loop run configs/offline/experiment_c_seed_314159.toml
```

Each command prints its exact content-addressed destination:

```text
<run.output_root>/<run.name>-<first-12-hex-of-config-SHA256>/
```

The default parent is `runs/`, which is ignored by Git. `data/` is reserved for
small, reviewable inputs and manifests; it is not the default destination for
generated trajectories, external provider data, or participant records.
Curated evidence belongs under `artifacts/` only after verification and
provenance review.

Conversation authoring is separate from dataset production:

```bash
cape-loop conversations generate-openrouter \
  data/scenarios/scenario-catalog-v1.json \
  data/scenarios/conversation-templates-v1.json \
  --model anthropic/claude-sonnet-5 --execute-live
```

The command can write a candidate JSON bank and the readable
provider-generation log
`data/scenarios/conversation-templates-v1.generation.jsonl`. The tracked log
preserves 24 historical candidate requests/results. The current tracked bank
was outcome-blind project-standardized afterward, so the log is candidate
authoring provenance rather than a provider-authorship claim for its visible
frame text. Subsequent runs consume the frozen JSON through
`[scenarios] conversation_file`; the log is not one row per simulated user.

The offline Gate 4 and Experiment C external-rescore source configurations:

```text
configs/offline/gate4_source.toml
configs/offline/experiment_c_rescore_source.toml
```

generate synthetic native states and blinded request packets. They make no
provider call. The broader `configs/offline/sensitivity.toml` run is a separate
22-point one-at-a-time robustness artifact and does not share the ordinary
A–C population/split layout.

Primary records are canonical JSON or JSON Lines:

- `.json` for one manifest, model bundle, summary, or aggregate object;
- `.jsonl` for event-, trajectory-, request-, response-, or metric-level rows;
- `.csv` for deterministic human-readable projections of retained canonical
  rows; and
- `.md` for deterministic human-readable previews or reports derived from
  retained canonical rows; and
- `.svg` for deterministic lightweight figures.

CSV, Markdown, and SVG outputs never replace the JSON/JSONL evidence from which
they were derived. Avoid opaque executable or binary serialization in released
data.

## Scenario catalog input

The canonical tracked stimulus input is
[`data/scenarios/scenario-catalog-v1.json`](../data/scenarios/scenario-catalog-v1.json).
Its strict generated schema is
[`scenario-catalog.schema.json`](../schemas/scenario-catalog.schema.json).
The top level binds catalog identity/version/status, eligibility, language and
locale, source and license, freeze dates, split and selection policies,
per-domain attribute order, authoring provenance, and the scenario array.
The loader accepts two coherent lifecycle states:
`frozen-development` with `simulation-and-pilot-only`, or `frozen-paper` with
`paper-eligible`. The latter is accepted only when every scenario is approved,
all three recorded reviews pass, and every scenario is marked paper-eligible.
This makes the release path executable without weakening the current
development catalog's boundary.

Each scenario records:

- globally unique scenario and family IDs, revision, provisional/approved
  status, split, domain, task family, and target attribute/key;
- the one declared nuisance attribute/key and its signed direction for the
  same-direction restricted peer;
- a neutral prompt and opaque wording-template ID;
- negative, positive, and two same-direction peer options, each with a unique
  ID, label, and exact three-number feature vector;
- supported mechanisms and machine-checkable quality assertions; and
- automated, surface-review, scientific-review, and paper-eligibility state.

The base options are `-0.5` and `+0.5` only on the target coordinate. Each
same-direction peer preserves that target value and adds either `-0.25` or
`+0.25` on exactly one of the other two coordinates. Version 1.4 declares that
coordinate and sign explicitly as `nuisance_attribute`, `nuisance_key`, and
`nuisance_direction`. Within each test domain-by-target cell, the six
scenarios cover both non-target attributes and both directions; across the
complete test bank, each numeric scenario-anchor signature occurs three
times. This counterbalancing is prospective structure, not evidence that the
visible prose has been semantically validated.

At runtime, the catalog supplies the scenario ID, task prompt, option
labels/features, and wording-template ID to `InteractionContext`. The optional
`prompt` property is emitted for catalog-backed records and included in
full-context and provenance-aware runtime rendering. Legacy contexts without a
catalog omit the optional property and remain valid.

### Frozen conversation-template input

The companion input is
[`data/scenarios/conversation-templates-v1.json`](../data/scenarios/conversation-templates-v1.json).
Its top-level fields are exactly:

```text
{
  schema_version: 1,
  bank_id: string,
  source: string,
  templates: [scenario template, ...]
}
```

The historical OpenRouter candidate-authoring response for one scenario
contained only:

```text
display_names
base_template
```

`base_template` is neutral. It contains `{prompt}`, `{option_1_name}`,
`{option_1_description}`, `{option_2_name}`, and
`{option_2_description}` exactly once each and ends in a question. It contains
no treatment placeholder. The candidate-authoring path expands that response
into a scenario record containing its `scenario_id`, four display-name
mappings, five `presentation_templates`, the fixed `choice_template`, and
source metadata.

The current stored bank was standardized after that candidate-authoring step;
its visible wording is not attributed to the provider that drafted historical
candidates. All 48 templates now carry
`project-standardized-neutral-frame-v1-unreviewed` as their source and use one
of three source-neutral base frames. Each frame appears exactly 16 times, and
each appears twice in every six-scenario test domain-by-target cell. This
outcome-blind machine balance reduces wording-frame confounding but is not
evidence of semantic validity, naturalness, neutrality, or human approval.

The stored forms remain compatible with the runtime renderer:

- `balanced`, `restricted`, and `ranking` share the same neutral base wording;
- `default` inserts only the fixed default sentence immediately after the
  rendered prompt;
- `suggested` inserts only the fixed suggestion sentence immediately after the
  rendered prompt; and
- `choice_template` is exactly `I choose {selected_name}.`

At runtime, the renderer follows the context's visible ranking, chooses the
matching presentation template, and creates:

```text
surface_id
assistant_message
user_message
display_names
source
```

The four stored display-name mappings form a validated scenario-specific A–D
name pool. They are not stable semantic labels at runtime. After the visible
ranking is fixed, the first displayed option receives the pool's A name and
the second receives its B name. Evaluated-model structured payloads separately
replace internal catalog IDs with `presented_option_1`,
`presented_option_2`, and so on. Internal IDs remain in retained audit records
only.

It receives neither latent truth nor numeric feature vectors. The structured
option is selected first by the response model. The exact rendered assistant
and user text then enters the observation and is therefore reused by every
updater assigned the same event.

Version 1.4.0 currently contains 48 scenarios, 48 distinct families, and 192
globally unique option IDs:

| Cell | Train | Development | Test |
| --- | ---: | ---: | ---: |
| Each travel attribute | 1 | 1 | 6 |
| Each writing attribute | 1 | 1 | 6 |
| Total scenarios | 6 | 6 | 36 |

All 48 are provisional, none is approved, and none is paper-eligible. The
catalog is `frozen-development` and `simulation-and-pilot-only`; its presence
does not make a generated run confirmatory evidence. The normative acceptance,
rejection, drafting, and human-review rules are in
[Scientific design](scientific-design.md#scenario-catalog-and-quality-policy).

The current writing surfaces deliberately use direct category descriptions
such as “formal,” “conversational,” “concise,” or “detailed.” They do not
contain complete alternative documents. This makes the primary instrument a
controlled test of whether an updater uses the declared causal context around
a recognizable preference category. It does not establish generalization to
natural drafting, subtle style inference, or full-text quality judgments. Such
claims require a separately versioned, split-disjoint, reviewed, and pretested
excerpt-based robustness bank.

Within a longitudinal trajectory, each domain-by-attribute pool is traversed
without replacement in a deterministic semantic-keyed order. Repetition starts
only after that pool is exhausted. Consequently, the current six-scenario test
cells cover a 16-turn cyclic trajectory without reuse (the three target cells
are visited 6, 5, and 5 times). The v2 exploratory policy also keeps target
counts within one at every prefix, so it visits every attribute once in each
three-turn block and has the same per-cell capacity bound. A custom or unknown
adaptive policy without that constraint is still audited conservatively as
though all turns could target one cell. These are capacity properties only;
they do not substitute for human review or semantic calibration.

### Prospective scenario-audit artifacts

`cape-loop scenarios audit CONFIG OUTPUT_DIR` writes three derived,
outcome-free files:

```text
scenario-audit.json                    # machine design/readiness report
scenario-review.md                     # metadata-visible researcher workbook
scenario-surface-review-blinded.md     # opaque dialogue-only review packet
```

The JSON distinguishes engineering-pilot, recorded-scientific-pilot, and paper
readiness. It includes the config-bound response coefficients, the complete
theta-by-susceptibility probability grid, both order-averaged estimands and
physical per-order binary-response bounds, policy-aware no-repeat capacity by
cell, raw label-length heuristics, rendered-language flags, cross-split lexical
overlap, within-selected-split lexical redundancy, exact cross-split
task-family reuse, and recorded review counts. The JSON also reports that the
72 test scenario-anchor instances reduce to 24 unique numeric signatures,
with each signature represented three times. It also reports joint
nuisance-attribute×direction balance and source-neutral conversation-frame
family balance.
The machine hygiene pass exhaustively renders 40 cases per selected scenario;
each Markdown packet keeps six previews per scenario. The blinded packet
removes scenario IDs, splits, targets, nuisance metadata, feature vectors,
option roles, and mechanism labels; the researcher packet retains those fields
for semantic inspection. Lexical and length checks make no semantic-validity
claim. None of these files changes catalog review fields or constitutes
verified human evidence.

Every configured catalog-backed run, including sensitivity, retains:

```text
inputs/scenario-catalog.json
inputs/scenario-catalog-manifest.json
inputs/conversation-templates.json
inputs/conversation-templates-manifest.json
metrics/scenario-coverage.json
metrics/scenario-consumption.json
```

The first file is the exact consumed byte sequence. The input manifest binds
its SHA-256, ID, version, status, eligibility, selection policy, counts, and
paper-eligibility flag. The availability coverage report enumerates every
domain×split×attribute cell, family count, task families, and declared
nuisance-attribute/direction coverage, and identifies itself as
`coverage_kind = "catalog_availability"`. Realized
train/development consumption is separately recorded under
`metrics/split-leakage-audit.json`, including missing
mechanism×target×direction cells and scenarios. Checked-in experiment
configurations allocate enough interactions to cover all 24 cells per domain;
smaller programmatic fixtures are reported as incomplete rather than silently
treated as complete. `scenario-consumption.json` repeats that
fitted-data audit and lists the unique scenarios actually used by the
experiment, including any available catalog scenarios not reached by the
configured workload. The same manifest is embedded at
`manifest.inputs.scenario_catalog` and copied to `metrics/summary.json` under
`scenario_catalog`. Reuse requires that retained binding to match the current
input.

`[scenarios].catalog_sha256` is checked before provider construction or run
artifact creation. Any byte change requires a new reviewed catalog
version/freeze and corresponding digest updates in configurations; editing a
completed run remains forbidden. The held-out terminal-v2 batteries are
separate generated evaluation instruments, not rows in this interaction
catalog.

## Splits and leakage controls

Splits assign complete semantic groups, not randomly selected rows:

| Axis | Executable boundary |
| --- | --- |
| Latent preference | One complete three-attribute `theta` tuple belongs to one split |
| Susceptibility | One complete ranking/default/suggestion tuple belongs to one split |
| Option surface | Feature-matched atlas, beacon, and cedar families are train, development, and test |
| Dialogue surface | Each split has a distinct visible wording-template family |
| Scenario surface | Each complete catalog family and its visible surfaces belong to one split |
| Paraphrase surface | A content-addressed paraphrase family belongs to exactly one split |

The opaque atlas/beacon/cedar names keep split labels out of model-visible
text while leaving surface identity auditable:

```text
train        -> atlas option/dialogue/scenario families
development  -> beacon option/dialogue/scenario families
test         -> cedar option/dialogue/scenario families
```

Training interactions fit likelihood models. Development users support
declared calibration and held-out diagnostics. Experiments A–C consume test
assets. The catalog loader rejects duplicate IDs, a family or wording-template
ID assigned across splits, missing domain×split×attribute coverage, and
normalized visible text repeated across splits. The concrete leakage audit
additionally binds catalog option IDs, wording IDs, family IDs, and
prompt/label surface fingerprints to the split manifest. Near-duplicate
semantic review remains a required human check rather than an automated claim.
The terminal-v2 battery adds separate test-only option IDs, feature values,
scenario families, wording IDs, and question types. Experiment A paraphrases
are content-addressed and checked against every train/development family,
content hash, and literal pattern.

Every A–C run retains:

```text
splits.json
metrics/split-leakage-audit.json
events/fitted-model-training.jsonl       # when events are retained
events/fitted-model-development.jsonl    # when events are retained
```

A concrete overlap or manifest/generator mismatch aborts the run. This proves
the implemented split execution, not that a researcher avoided consulting test
results while tuning an untracked prompt or threshold.

## Run directory and output lifecycle

A successful A–C run is self-describing:

```text
runs/<run-id>/
├── config.resolved.json
├── config.source.toml
├── environment.json
├── manifest.json
├── splits.json
├── inputs/
│   ├── scenario-catalog.json
│   ├── scenario-catalog-manifest.json
│   ├── conversation-templates.json
│   └── conversation-templates-manifest.json
├── population/
│   └── users.jsonl
├── events/
├── analysis/
├── conversations/
├── decoder/
├── llm/
├── metrics/
│   └── summary.json
├── models/
├── tables/
├── figures/
└── SHA256SUMS
```

Directories are created as needed, so an experiment without LLM or decoder
records may leave the corresponding directory empty. Sensitivity uses its own
point-specific fit and trajectory layout.

`inputs/conversation-templates.json` is the exact bank consumed by the run.
`inputs/conversation-templates-manifest.json`, also embedded under
`manifest.inputs.conversation_templates`, records its bank ID, declared source,
scenario count, and retained path.
Each full interaction event carries the mathematical `selected_option`, exact
`assistant_message`, exact user `surface_response`, and `surface_id`.
`analysis/*.jsonl` remains a compact metric projection and may omit full
dialogue. A separate normalized projection under `conversations/` groups the
same retained exchanges with their metrics for human inspection; it does not
run the simulator again or create another observation. Evaluated writer
requests and responses belong under `llm/`. The separate authoring record
remains `data/scenarios/conversation-templates-v1.generation.jsonl`.

The identity and control files are:

| File | Contract |
| --- | --- |
| `config.resolved.json` | Canonical validated configuration; its SHA-256 determines the run suffix |
| `config.source.toml` | Exact CLI input, including comments; absent only for a hash-bound programmatic config origin |
| `environment.json` | Python implementation/version, platform, and executable |
| `manifest.json` | Run/config/source identity, config origin, bound inputs including the scenario catalog, deterministic declaration, and `created`/`complete`/`failed` status |
| `SHA256SUMS` | Complete inventory of every retained file except itself |

Shared A–C preparation normally adds:

```text
population/users.jsonl
models/raw-fitted-likelihoods.json
models/fitted-likelihoods.json
models/calibration.json
models/held-out-response-diagnostics.json
metrics/split-leakage-audit.json
```

Experiment-specific event and metric names are documented in the record tables
below. All experiment summaries and gate reports retain a no-claim boundary.
Conditional event files are governed by `[artifacts].retain_events`; some
evaluation definitions remain unconditional because later verification needs
them. Newly generated Experiment A–C runs also write one compact analysis
projection under `analysis/`, independently of raw event retention. The
projection is derived from the records already evaluated by the runner and
does not represent additional synthetic or external observations.
A–C and sensitivity runs also write their exhaustive normalized conversation
JSONL and bounded Markdown preview independently of raw event retention. A
legacy or programmatic run without a natural surface retains the trace with
`surface_available = false` and nullable surface fields rather than inventing
dialogue.

Live LLM runs additionally retain the consumed exchange and its evidence:

```text
llm/input-manifest.json
llm/request-preflight.json
llm/requests.jsonl                    # when prompts are retained
llm/responses.jsonl
llm/exchange-manifest.json
llm/provider-audit.jsonl              # live mode
llm/transport-attempts.jsonl          # live mode
llm/provider-manifest.json            # live mode
models/llm-calibration.json
llm/development-raw-responses.jsonl   # temperature mode
metrics/llm-development-calibration.jsonl
llm/test-raw-responses.jsonl          # temperature mode
```

Recovery journals remain outside the immutable run. External decoder,
native-action, Gate 4, Experiment C rescore, Gate 6, human, and optional R
outputs likewise live in separate checksum-bound directories and refer to
their source runs by digest. See [Live execution](live-execution.md) for those
collection and admission workflows.

Verify a completed run before analysis:

```bash
PYTHONPATH=src python -m cape_loop verify runs/<run-id>
```

Verification requires a complete manifest, matching directory/run/config
identity, a valid source-config origin, a summary, no symlinks, and exact
agreement between `SHA256SUMS` and the retained tree. It establishes integrity,
not experimental completeness or a scientific claim.

Freeze a verified run into a deterministic archive:

```bash
PYTHONPATH=src python -m cape_loop artifact freeze \
  runs/<run-id> artifacts/<release-id>.tar
PYTHONPATH=src python -m cape_loop artifact verify \
  artifacts/<release-id>.tar
```

The archive and sidecar bind normalized members, source run and config
identity, source manifest/checksum digests, and archive SHA-256. Freezing does
not promote a smoke or pilot to paper evidence.

Completed runs are immutable: their exact `SHA256SUMS` inventory must not be
changed to add a newly introduced projection. A historical verified A–C run can
instead be projected into a separate compact directory:

```bash
PYTHONPATH=src python -m cape_loop artifact compact \
  runs/<run-id> artifacts/<compact-id>
PYTHONPATH=src python -m cape_loop artifact verify-compact \
  artifacts/<compact-id>
```

That directory contains `analysis-rows.jsonl`, `manifest.json`, and
`SHA256SUMS`. Its manifest binds the source run identity, source checksum
evidence, and exact exporter-source digest; it is not itself a full run, a new
observation set, or a replacement for the complete frozen run archive.

On failure, `manifest.json` has `status = "failed"` and `failure.json` records
the exception. Such a directory may be useful for diagnosis but is incomplete
and ineligible for analysis. Do not hand-edit a run: any change invalidates its
checksums.

## External and sensitive records

The synthetic dataset does not include OpenAI/OpenRouter responses, selected
Claude/Gemini judgments, optional direct decoder replications, native
provider-produced actions, or human ratings. Those are separately collected
external evidence with their own requests, audits, terms, and release review.

`population/users.jsonl`, event files, decoder truth labels, and researcher
codebooks may contain evaluator-only truth or linkage. They must never be fed
to an updater or decoder merely because they live in the same local run.

Do not commit participant identifiers, contact details, platform IDs, free
text, or unreviewed codebooks. Human collection requires an appropriate ethics
determination, compatible consent, de-identification, privacy/retention rules,
and release authorization. Synthetic data can still encode stereotypes or
problematic templates and requires review before release. See
[Ethics and limitations](ethics-and-limitations.md).

## Versioning and nesting

`schema_version` is attached only where the current producer adds it.

| Record or artifact | v1 version carrier |
| --- | --- |
| latent user release row | top-level `schema_version: 1` |
| LLM request and response | top-level `schema_version: 1` |
| run/split/exchange/packet manifests and calibration/fitted-model/gate records | top-level `schema_version: 1` |
| generated interaction record | `$id` ends in `interaction-record:v1`; no `schema_version` property |
| generated trajectory record | `$id` ends in `trajectory:v1`; no `schema_version` property |
| generated human rating | `$id` ends in `human-rating:v1`; no `schema_version` property |
| option, context, provenance, observation, profile update, and belief dictionaries | no independent version field |

Runner event files commonly add `schema_version: 1` to the outer JSONL row.
They do not recursively add it to nested `context`, `policy_provenance`,
`observation`, `profile_update`, belief, native-state, or `audit_record`
objects. A nested gate report is an exception because `GateReport.to_dict()`
itself is versioned.

Consequently, validate a record against the schema named for that record. For
example, validate `audit_record` against `trajectory.schema.json`; do not add a
`schema_version` field first, because that schema has
`additionalProperties: false`.

## Scalar and array conventions

- `theta` is a length-three integer array. Each element is one of
  `[-2, -1, 1, 2]`.
- An option's `features` is a length-three numeric array, not an
  attribute-keyed object.
- Attribute positions are `0`, `1`, and `2`. Their human meanings come from
  the domain specification.
- A susceptibility is an object with numeric `ranking`, `default`, and
  `suggestion` values. Values are finite and non-negative.
- Belief arrays use the fixed value order `[-2, -1, 1, 2]`.
- Tuples in Python serialize as JSON arrays. Tuple pairs such as a provenance
  snapshot serialize as JSON objects where the serializer explicitly calls
  `dict(...)`.
- JSON written through `RunArtifacts` is emitted with sorted keys and compact
  separators. Array order remains semantically significant.
- Fields explicitly named as SHA-256 digests, such as `prompt_sha256`,
  `source_sha256`, and `state_id`, are lowercase 64-character strings.

The two implemented domains both have three attributes:

| Position | Travel | Writing |
| --- | --- | --- |
| `0` | budget ↔ premium | concise ↔ detailed |
| `1` | central ↔ comfort | formal ↔ conversational |
| `2` | convenience ↔ flexibility | British ↔ American |

## Latent user release row

`LatentUser.to_dict()` returns only `user_id`, `theta`, and
`susceptibility`. The versioned release row in `population/users.jsonl` is
produced by `population.user_state_record()` and has exactly the following
shape (the values are illustrative, not the first user under a public seed):

```json
{
  "schema_version": 1,
  "user_id": "shared-test-user-00000",
  "domain": "travel",
  "theta": [-2, 1, 2],
  "susceptibility": {
    "ranking": 0.15,
    "default": 0.45,
    "suggestion": 0.85
  },
  "split": "test"
}
```

`domain` is either `travel` or `writing`; `split` is `train`,
`development`, or `test`. The same shared latent user may appear once per
selected domain in the population artifact. Latent user rows are
simulator/evaluator data and must not be passed to an updater.

For an experiment configured with \(N\) test users, the ordinary A–C
preparation path generates \(N\) test users,
\(\max(24,\min(128,4N))\) training users, and \(\max(8,N)\) development
users. These are deterministic synthetic allocations, not sampled estimates
of population prevalence.

## Option

`Option.to_dict()` has exactly four keys:

```json
{
  "option_id": "travel_price_neg",
  "features": [-0.5, 0.0, 0.0],
  "label": "budget",
  "domain": "travel"
}
```

Presentation effects are not option features. Ranking, default, suggestion,
wording, and question type belong to the interaction context.

## Interaction context

`InteractionContext.to_dict()` uses the concrete field names `default`,
`suggested_option`, and `wording_template`:

```json
{
  "context_id": "travel-anchor:default:0",
  "domain": "travel",
  "scenario_id": "travel-anchor",
  "turn_id": "0",
  "options": [
    {
      "option_id": "travel_price_neg",
      "features": [-0.5, 0.0, 0.0],
      "label": "budget",
      "domain": "travel"
    },
    {
      "option_id": "travel_price_pos",
      "features": [0.5, 0.0, 0.0],
      "label": "premium",
      "domain": "travel"
    }
  ],
  "ranking": ["travel_price_neg", "travel_price_pos"],

  "wording_template": "neutral_matched_choice",
  "question_type": "choice",
  "target_attribute": 0,

```

`ranking` must be an exact permutation of the displayed option IDs. `default`
and `suggested_option` are either a displayed option ID or `null`.
`target_attribute` is `0`, `1`, `2`, or `null`. This is the canonical internal
record used by the simulator and evaluator. Its numeric features and target
index are deliberately omitted from the evaluated LLM projection. The context
contains no policy ID or latent truth.

## Policy provenance

`PolicyProvenance.to_dict()` has no provenance ID or context ID:

```json
{
  "policy_id": "soft_profile_conditioned",
  "policy_version": "v1",
  "profile_snapshot": {
    "attribute_1": -0.4,
    "attribute_2": 0.2,
    "attribute_3": 0.0
  },
  "random_seed": 187653210,
  "config_digest": "",
  "presentation_mechanism": "default",
  "profile_conditioned": true
}
```

Current built-in policies leave `config_digest` empty; the record type permits
callers to populate it with a string. `profile_snapshot` is a sorted
string-to-number object, normally the policy-visible expected preference per
attribute. It is not a posterior distribution. `presentation_mechanism`
records the channel actually applied, while `profile_conditioned` says whether
the current profile causally selected that treatment; a logged snapshot or
policy name alone is not evidence of conditioning.

Provenance is a sibling of the visible context in an interaction record. Only
the provenance-aware updater view receives it.

## Observation

`Observation.to_dict()` has exactly:

```json
{
  "selected_option": "travel_price_neg",
  "surface_response": "I choose Hotel A.",
  "choice_noise_key": "experiment-a:travel:user-000:turn-0",
  "assistant_message": "Here are two lower-cost hotel options for your trip. Hotel A is a standard room in a mixed-use neighborhood. Hotel B is a standard room in a quiet outer neighborhood. Which would you like?",
  "surface_id": "travel-anchor:restricted:travel_price_neg>travel_price_peer:travel_price_neg"

```

`assistant_message` and `surface_response` are the exact two-turn exchange
shown to a full-context updater. When `assistant_message` is present,
`surface_response` and `surface_id` are required. `surface_response` may remain
`null` only for legacy or explicitly non-conversational fixtures.
`choice_noise_key` may be empty but is always a string. The selected option
must occur in the associated context when the observation is placed in an

## Profile update

`ProfileUpdate.to_dict()` contains raw arrays rather than state references:

| Key | Current representation |
| --- | --- |
| `updater_id` | string |
| `belief_before` | 64 theta-joint probabilities |
| `belief_after` | 64 theta-joint probabilities |
| `native_memory_before` | empty array, or `[state_id, persona_text]` for a native updater |
| `native_memory_after` | empty array, or `[state_id, persona_text]` for a native updater |
| `written_delta` | array of diagnostic strings |

All current updaters write 64-element, normalized `belief_before` and
`belief_after` vectors. The exported interaction schema and the standalone
`ProfileUpdate` constructor permit any non-negative vector length and do not
require normalization; the stronger guarantee comes from the current updater
producers. The arrays are public theta beliefs; the exact updater's private
theta-by-susceptibility state is not included in `ProfileUpdate` itself.

`UpdaterState.to_dict()` is the complete runtime state envelope:

```text
{
  updater_id: string,
  turn: integer,
  event_ids: [string, ...],
  belief: PreferenceBelief,
  joint_belief?: JointThetaPsiBelief,
  opaque_state?: object
}
```

This is shape notation, not literal JSON. `joint_belief` is present only for an
updater that keeps a theta-by-susceptibility posterior. `opaque_state` is
present only when the private state exposes a mapping-valued `to_dict()`;
native memory states do. `UpdateResult.to_dict()` wraps this under `state`
beside `profile_update` and a string-keyed `diagnostics` object.

## Beliefs

Belief serializers do not include `schema_version`.

### Marginal belief

`MarginalPreferenceBelief.to_dict()` is a three-by-four array:

```json
{
  "kind": "marginal",
  "values": [-2, -1, 1, 2],
  "probabilities": [
    [0.25, 0.25, 0.25, 0.25],
    [0.25, 0.25, 0.25, 0.25],
    [0.25, 0.25, 0.25, 0.25]
  ]
}
```

Row `a`, column `v` is the marginal probability for attribute position `a`
and value `values[v]`.

### Theta-joint belief

`PreferenceBelief.to_dict()` has:

```text
{
  kind: "theta_joint",
  theta_states: [[-2, -2, -2], ..., [2, 2, 2]],
  probabilities: [p_0, ..., p_63],
  marginals: [[p_0,-2, ..., p_0,+2], ..., [p_2,-2, ..., p_2,+2]]
}
```

This is shape notation, not literal JSON. `theta_states` contains all 64 states
in lexicographic product order induced by `[-2, -1, 1, 2]`; `probabilities[i]`
belongs to `theta_states[i]`. `marginals` is a three-by-four numeric array
without a nested `kind` or `values` key.

### Theta-by-susceptibility belief

`JointThetaPsiBelief.to_dict()` has:

```text
{
  kind: "theta_psi_joint",
  theta_states: 64 length-three arrays,
  susceptibilities: N objects with ranking/default/suggestion,
  probabilities: 64 * N numbers,
  theta_marginals: a 3 x 4 array,
  susceptibility_marginal: N numbers
}
```

This is shape notation, not literal JSON. The flat probability vector is
theta-major:

```text
flat_index = theta_index * N + susceptibility_index
```

The exact action-aware updater retains this object at runtime in
`UpdaterState.joint_belief`, and its public `UpdaterState.belief` must equal the
theta marginal. `UpdaterState.to_dict()` includes `joint_belief` when present,
and `UpdateResult.to_dict()` delegates to that complete state serializer. The
core `ProfileUpdate` and `TrajectoryRecord` audit chain still contain only the
public theta belief; experiment event rows retain the private joint state
separately.

### Experiment-specific belief retention

- In memory, `ExperimentARow.to_dict()` defaults to
  `include_joint_states=True`. Its result contains full theta-joint `prior`,
  `posterior`, `fitted_aware_posterior`, and `exact_posterior` objects; all four
  three-by-four marginal projections; nullable `posterior_theta_psi` and
  `exact_theta_psi`; `prior_stratum`, numeric `prior_strength`; and
  `exact_reference_id`. `posterior_theta_psi` is
  populated when the evaluated updater is exact action-aware, while
  `exact_theta_psi` is the exact reference state.
- The runner normalizes retained Experiment A events to avoid repeating that
  reference once per updater. `events/experiment-a.jsonl` calls
  `to_dict(include_joint_states=False)`: each versioned row keeps `prior`,
  `posterior`, `fitted_aware_posterior`, all four marginal projections, and
  `exact_reference_id`, but omits `exact_posterior`,
  `posterior_theta_psi`, and `exact_theta_psi`.
  `events/experiment-a-exact-references.jsonl` stores one versioned row per
  trial with exactly `schema_version`, `exact_reference_id`,
  `exact_posterior`, and `exact_theta_psi`. Join updater rows to the retained
  exact state by `exact_reference_id`.
- Experiment B retained trajectories store full theta-joint
  `initial_belief`, `terminal_belief`, and `terminal_shadow_belief` objects.
  They also store nullable `terminal_joint_belief` and
  `terminal_shadow_joint_belief`. Each turn stores full before/after system and
  shadow theta beliefs plus nullable system and shadow theta-by-susceptibility
  states. The turn record also carries `action_aware_information_gain` and
  `information_gain_state_space` beside its false-confidence, LCG, regret, and
  action-influence diagnostics.
- Experiment C replay results store full initial and terminal theta-joint
  beliefs and the complete serialized `terminal_state`, including joint or
  opaque state when present. Endogenous trajectories use the Experiment B
  layout. Evaluation metric rows store scores, not posterior arrays.

These experiment-level states are written only when event retention is enabled.
The experiment metrics do not duplicate the posterior arrays.

For a `ClosedLoopTurn`, `action_aware_information_gain` is the proposal-defined
entropy reduction

```text
H(shadow_before) - H(shadow_after)
```

computed from the action-aware same-history shadow. When both shadow joint
states are available, entropy is taken over the complete theta-by-susceptibility
posterior and `information_gain_state_space` is `theta_psi_joint`. The fallback
uses the 64-state theta posterior and records `theta_joint`. Entropy uses natural
logarithms, and a trajectory's `cumulative_information_gain` is the sum of these
per-turn values.

## Native memory state

`NativeMemoryState.to_dict()` has this exact key set:

| Key | Representation |
| --- | --- |
| `memory_kind` | `episodic`, `semantic`, or `provenance_linked` |
| `base_belief` | raw 64-element theta probability array |
| `episodes` | array of `NativeEpisode` objects |
| `claims` | array of `SemanticClaim` objects |
| `persona_belief` | raw 64-element theta probability array |
| `persona_text` | deterministic three-attribute summary |
| `state_id` | SHA-256 of the other six fields in canonical form |

A native episode has exactly:

```json
{
  "event_id": "trajectory-001:turn-0",
  "selected_option_id": "travel_price_neg",
  "target_attribute": 0,
  "selected_direction": -1,
  "visible_mechanisms": ["default"],
  "displayed_directions": [-1, 1],
  "evidence_weight": 0.35,
  "surface_response": null,
  "provenance_policy_id": null,
  "provenance_profile_snapshot": {},
  "provenance_presentation_mechanism": null,
  "provenance_profile_conditioned": null
}
```

For provenance-linked memory, the final four provenance fields are populated.
A semantic claim has exactly:

```json
{
  "attribute": 0,
  "direction": -1,
  "confidence": 0.71,
  "source_event_ids": ["trajectory-001:turn-0"],
  "cumulative_evidence_weight": 0.35
}
```

Episodic memory retains episodes and leaves `claims` empty. Semantic and
provenance-linked memory retain episodes, consolidate claims, and update the
persona projection.

When `artifacts.retain_events = true`, Experiment B trajectory rows retain the
complete native state before and after every turn and again under
`terminal_native_state`. Experiment C replay rows retain a complete terminal
native state, while endogenous rows use the same per-turn and terminal layout
as Experiment B. When event retention is disabled, those native-state payloads
are not written to event files; derived decoder metrics are still written.

The `profile_update` inside an audit record stores only `[state_id,
persona_text]` before and after, not the complete native payload.

### Blinded native decoders

`blinded_decoder_views()` produces two `BlindedDecoderView` dictionaries:

```text
{
  decoder_id: "direct_semantic_v1" | "history_evidence_v1",
  pseudonymous_state_id: string,
  payload: object
}
```

This is shape notation, not literal JSON. The outer view is not independently
versioned. Its `payload` does contain `schema_version: 1`. The direct payload
contains `persona_summary`, three `direction_confidence` entries, and
`semantic_claims`; the history payload contains `prior_marginals` and
redacted episode evidence. Source event IDs in both payloads are replaced by
decoder-local `event-NNNN` pseudonyms; raw event IDs may encode user,
condition, policy, or updater labels and never cross the decoder boundary.
Experiment metric rows retain decoder ID,
pseudonymous state ID, and terminal scores, not the decoded probability vector.

## Compact analysis rows

The full event records preserve causal chains, probability distributions,
same-history shadows, and native memory needed for audit and reconstruction.
They can be large because those states are repeated at each turn. The runner
therefore writes narrow JSON Lines projections for routine analysis:

| File | Row unit | Fields |
| --- | --- | --- |
| `analysis/experiment-a-rows.jsonl` | One evaluated updater×trial pair across both response modes | `schema_version`, one-based `source_record_index`, `trial_id`, `user_id`, `domain_id`, `scenario_id`, `updater_id`, `mechanism`, `prior_strength`, `response_mode`, `update_error` |
| `analysis/experiment-a-exclusions.jsonl` | One excluded matched set | `schema_version`, `user_id`, `domain_id`, `target_attribute`, `anchor_direction`, `minimum_probability`, `choice_probabilities` |
| `analysis/experiment-b-turns.jsonl` | One retained turn from one trajectory | `schema_version`, one-based `source_record_index`, zero-based `source_turn_index`, `trajectory_id`, `user_id`, `domain_id`, actual per-turn `scenario_id`, `crn_key`, `updater_id`, `policy_id`, `initial_profile_condition`, one-based `turn`, `terminal_error`, repeated `retained_terminal_error`, `same_history_shadow` |
| `analysis/experiment-c-rows.jsonl` | One existing fixed-history or endogenous evaluation/ranking row | `schema_version`, one-based `source_record_index`, `split`, `regime`, `replicate`, `user_id`, `domain_id`, `updater_id`, `profile_error`, `behavioral_accuracy`, nullable `cross_context_accuracy`, `intrinsic_regret`, `score_basis`, `history_digest`, `battery_id`, `battery_digest` |

Experiment A's compact `update_error` is the registered fitted-reference
action-conditioned update error (ACUE); exact-oracle ACUE and KL remain in the
experiment metric/event rows rather than changing this registered projection.
In Experiment B, `terminal_error` is the per-turn marginal Brier error;
`retained_terminal_error` repeats the trajectory's retained terminal Brier and
matches the last compact turn. `same_history_shadow` is a Boolean confirming
that the shadow consumed the same retained history, not the full joint
posterior. `scenario_id` names the stimulus actually displayed on that turn.
`crn_key` instead identifies the complete counterfactual policy/updater twin
set whose compatible choice draws and scenario-occurrence schedules share a
common random-number key. These are different grouping variables: a branch can
show a different scenario after its endogenous target sequence diverges while
remaining in the same CRN set.

These are deterministic projections, not independent sources of numerical
truth. For a newly generated run they are written before finalization, listed
in the run's `SHA256SUMS`, and reported through `analysis_artifact` and
`analysis_row_count` in `metrics/summary.json`. Setting
`artifacts.retain_events = false` can omit configured raw audit events but does
not suppress these analysis rows. A's summary also names
`analysis_exclusion_artifact`; the exclusion projection remains available even
when its raw event counterpart is omitted. Sensitivity has no corresponding
file because `metrics/sensitivity*.jsonl` and `tables/sensitivity.csv` already
contain compact aggregate rows.

## Conversation logs and readable previews

A–C and sensitivity runs write exactly one experiment-matching pair:

| Run kind | Exhaustive trace | Human preview |
| --- | --- | --- |
| Experiment A | `conversations/experiment-a.jsonl` | `conversations/experiment-a.md` |
| Experiment B | `conversations/experiment-b.jsonl` | `conversations/experiment-b.md` |
| Experiment C | `conversations/experiment-c.jsonl` | `conversations/experiment-c.md` |
| Sensitivity | `conversations/sensitivity.jsonl` | `conversations/sensitivity.md` |

The live one-scenario diagnostic writes one record with the same public
contract to `OUTPUT_DIR/conversation.jsonl`, using `experiment = "demo"` and
`conditions.demonstration_only = true`; it does not add an experiment
observation or a new dataset category. The complete explanatory payload
remains separately available as `OUTPUT_DIR/result.json`.

The JSONL is exhaustive. Each line is one normalized logical conversation,
with this containing shape:

```text
{
  schema_version: 1,
  record_kind: "conversation_trace",
  experiment: "A" | "B" | "C" | "sensitivity" | "demo",
  conversation_id: string,
  conversation_kind: "single_turn" | "closed_loop" | "fixed_history",
  source_id: string,
  user_id: string,
  domain_id: "travel" | "writing",
  conditions: object,
  dialogue: [dialogue turn, ...],
  outcomes: [evaluation outcome, ...],
  assessments: [derived assessment, ...],
  comparisons: [derived comparison, ...]
}
```

A dialogue turn has:

```text
{
  turn: positive integer,
  event_id: string,
  scenario_id: string | null,
  surface_id: string | null,
  surface_available: boolean,
  assistant: string | null,
  user: string | null,
  selected_option_id: string,
  selected_option_label: string | null,
  presentation_mechanism: string,
  choice_source: "mathematical_user_simulator",
  surface_source: string | null,
  turn_metrics: object
}
```

When `surface_available` is true, `assistant` is the frozen scenario
presenter's turn; it is not an answer generated by the evaluated profile
writer. `user` is the natural realization of the option already selected by
the mathematical user simulator. `selected_option_label` is the display name
resolved from the configured bank, and `surface_source` is that frozen
template's actual source metadata. Without a configured surface, those fields,
`surface_id`, and possibly `scenario_id` are `null`; the structured choice
remains available.

The evaluated writer appears under `outcomes`. Every outcome contains
`updater_id`, nullable `updater_view`, a possibly empty unique `model_ids`
array, and a nonempty exact `metrics` object. This role separation prevents a
readable trace from implying that the authoring LLM, simulated user, and
evaluated writer are the same agent. All 13 containing fields shown above are
required even when `assessments` or `comparisons` is empty.

Normalization follows the estimand:

- A uses one trace per `trial_id` and groups all updater outcomes that consumed
  that same exchange;
- B uses one trace per closed-loop trajectory and keeps all turns in order;
- C stores a fixed history once across its replayed updater outcomes, while
  endogenous updater-dependent histories remain separate; and
- sensitivity uses the B trajectory form, writes one trace per trajectory, and
  retains `sensitivity_point_id` and the rest of that point's coordinates in
  `conditions`.

B and sensitivity turn metrics include the evaluator-only balanced action
signature, visible-action divergence, profile-aligned treatment, and
reinforcement-event indicator where defined. Their terminal/comparison metrics
include initial and terminal error, EAR, CEC, reinforcement-event rate, and,
for matched soft/exploratory B branches, action-aware disconfirmation deficit.
These values describe the same retained trajectories; they are not additional
observations.

The trace deliberately excludes latent theta and susceptibility, numeric option
feature vectors, posterior and joint-belief arrays, native-memory payloads,
provider request bodies, and repeated copies of the frozen template bank.
Those remain in their canonical evaluator, event, LLM, or input artifacts.
The trace keeps exact unrounded metric values; only its Markdown rendering may
round values for display.

The Markdown file is a deterministic, condition-diverse preview capped at 100
trace records by default. It states that it is a readable preview of X of Y
complete conversation records, points to the exhaustive JSONL, and reports the
exact complete dialogue-turn and evaluated-updater-outcome counts. Selection
round-robins across the available experiment, domain, conversation kind,
sensitivity point, regime, mechanism, policy, and first-updater groups. The
preview also expands metric keys into readable labels and supplies
interpretation guidance:

- Brier/profile error, ACUE, KL divergence, and regret are better when lower;
- behavioral, cross-context, and update-direction accuracy are better when
  higher;
- information gain measures learning and is not itself an accuracy score;
- update magnitude and evidence weight describe the size of an update rather
  than whether it was correct; and
- laundered-confidence gain and false-stability assessments are risk
  diagnostics, so a positive value is not an improvement.

Every experiment summary exposes the exact keys:

```text
conversation_log_artifact
conversation_log_markdown_artifact
conversation_record_count
conversation_turn_count
conversation_outcome_count
conversation_markdown_preview_count
```

`conversation_record_count` is the number of exhaustive JSONL lines,
`conversation_turn_count` is the sum of their `dialogue` lengths,
`conversation_outcome_count` is the sum of their `outcomes` lengths, and
`conversation_markdown_preview_count` is the number of trace records rendered
in Markdown. The first three are complete-run counts; only the last is bounded
by the preview limit. The traces are generated from already evaluated in-memory
records, remain available when raw event retention is disabled, and do not
increase the experiment's sample size.

```text
request_id / request_sha256 / pseudonymous_state_id
evaluation_split / regime / user_id / domain_id / replicate / updater_id
source_metric_row_sha256 / stable_row_key_sha256
source_state_file / source_state_record_id / source_state_record_sha256
terminal_state_id / terminal_state_sha256
battery_id / battery_digest
```

The external rescore admits exactly two complete family/instance/source
descriptors. Each `experiment-c-external-score` row binds one calibrated family
judgment to the exact request, source metric row, native state, common terminal
battery, and full terminal score. The derived
`metrics/experiment-c-rescored.jsonl` preserves every non-native source row
byte-for-byte at the parsed-object boundary and changes only the declared
native score fields. `review.json`, `manifest.json`, and `SHA256SUMS` bind the
source run, canonical retained judgments, calibration, rankings, ESR, and Gate
5. See [Live execution](live-execution.md#experiment-c-external-rescore).

`review.json` distinguishes provenance from source-design metadata. With the
complete selected OpenRouter Claude/Gemini collection,
`validation.source_design.provenance_mode` is
`selected_openrouter_gateway_collection`; the review retains the validated
per-model journals, combined collection inputs, and gateway summary while
recording `gateway_provenance_validated = true`,
`provider_provenance_validated = false`, `shared_gateway = true`,
`distinct_transport_origins = false`, and
`first_party_origin_claimed = false`. The optional direct-origin mode
uses `validated_direct_first_party_collection` and records its separate
first-party-provider validation. In the explicit generic mode,
`validation.source_design.provenance_mode` is
`reviewed_generic_judgments`,
`validation.source_design.provider_provenance_validated` is false, and decoder
origin/family/source fields remain caller-declared. None of these modes claims
statistically independent errors.

### Experiment C multi-seed review

`experiment-c-robustness review` writes a separate three-file derived artifact,
never a child of a source run:

```text
review.json
manifest.json
SHA256SUMS
```

`review.json` is a schema-versioned object with
`artifact_kind = "experiment-c-multiseed-robustness-review"` and
`claim_status = "not_claimed"`. It binds 2–32 source run IDs, seeds, executable
source digests, normalized scientific-config digests, source checksum-manifest
digests, and the exact config/ranking/gate/summary artifact digests. Each source
entry embeds its retained clustered-bootstrap method/count/cluster metadata and
the point-ranking, inferential-order, Gate 5, and ESR-selection observations
used by the aggregate.

The `comparisons` object has nine fixed dimension IDs. Each value contains
content-addressed patterns, source IDs/seeds, exact rational modal and pairwise
agreement proportions, and explicit pairwise disagreements. `overall` reports
the exact unanimous-dimension fraction and always carries
`scientific_claim_inferred: false`. The content-derived `artifact_id` binds the
whole review excluding that field itself.

The review manifest binds the review digest, artifact ID, normalized config
digest, source count, and a run-ID-to-source-`SHA256SUMS` digest map. Its own
`SHA256SUMS` permits only `review.json` and `manifest.json`; extra files,
directories, symlinks, duplicate/unsafe paths, and non-finite JSON are invalid.
See [Experiments](experiments.md#experiment-c-evaluation-validity).

### Gate 6 cross-run review

The Gate 6 declaration contains explicit researcher-controlled pair, family,
provider-source, requested-model, returned-model, and optional OpenRouter
upstream identities. Each source reference binds a run ID and the digest of its
`SHA256SUMS`. The importer does not infer family identity or statistical
independence from those strings.

`evidence/pairs.jsonl` retains one recomputed evidence object for every declared
sensitivity-to-Experiment-A pair. It binds both verified run inventories,
provider request/response/audit/transport evidence, normalized sensitivity
configuration, four within-run robustness results, and the held-out
paraphrase-transfer result traced to exact `llm_full_context` responses.
`metrics/gate-6.json` is the ordinary six-criterion `GateReport`; review and
manifest objects bind its digest and keep `claim_status = "not_claimed"`. See
[Live execution](live-execution.md#gate-6-cross-run-review).

## Manifests and integrity records

### Run manifest

`manifest.json` is deliberately small and matches
`run-manifest.schema.json` exactly:

```json
{
  "schema_version": 1,
  "run_id": "experiment-a-smoke-0123456789ab",
  "config_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "config_origin": {
    "kind": "toml_file",
    "retained_file": "config.source.toml",
    "source_filename": "smoke.toml",
    "source_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
    "config_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
  },
  "git_revision": null,
  "source_sha256": "abcdef0123456789abcdef0123456789abcdef0123456789abcdef0123456789",
  "deterministic": true,
  "status": "complete"
}
```

`config_origin` is either a retained TOML identity or a descriptor and digest
for a programmatically supplied `AppConfig`. When TOML is retained, verification
reparses it and requires its resolved digest to match `config.resolved.json`.

`status` is `created`, `complete`, or `failed`. The manifest does not embed the
configuration, environment, metrics, failures, or file checksums. Those are
separate records:

- `config.resolved.json`;
- optional byte-for-byte `config.source.toml`;
- `environment.json`;
- `metrics/summary.json`;
- `failure.json` for a failed run;
- `SHA256SUMS` when checksum generation is enabled.

`source_sha256` covers Python files under `src/cape_loop`, `py.typed`, and
`pyproject.toml`. `SHA256SUMS` covers every materialized run file except the
checksum file itself.

### Split manifest

`splits.json` contains `schema_version`, `seed`, and six string-to-split maps:
`theta_groups`, `susceptibility_groups`, `option_templates`,
`dialogue_templates`, `scenario_families`, and `paraphrase_templates`.
Map values are `train`, `development`, or `test`. A manifest using either v2
population policy has `schema_version = 2` and also records the selected
nonlegacy `theta_policy` and/or `susceptibility_policy`. An all-legacy manifest
retains schema version 1 and omits those fields for exact replay compatibility.

The official v2 policies use split-disjoint orthogonal supports: theta has 32
train, 16 development, and 16 test profiles; susceptibility has nine profiles
in each split. When both are active, user allocation uses a cached,
outcome-blind joint block search that preserves the two balanced orders while
reducing cross-coordinate contingency imbalance and linear association at the
official sample horizons. It does not enumerate their Cartesian product for
every small run and does not assert finite-sample independence.

`metrics/split-leakage-audit.json` binds those declarations to the concrete
assets consumed by the generators. It contains `status`, the six independent
axes, per-split asset counts, pairwise overlap maps, checked manifest bindings,
and the paraphrase-suite digest. A completed run can contain only
`status: "passed"` because an overlap aborts execution.

### LLM exchange manifest

`llm/exchange-manifest.json` contains:

```text
{
  schema_version: 1,
  prompts_retained: boolean,
  requests: [
    {request_id, updater_id, view, prompt_sha256},
    ...
  ],
  models: [model_id, ...]
}
```

This is shape notation, not literal JSON. Responses are written in a completed
run when an LLM replay updater is active. Full requests are written only when
`artifacts.retain_prompts = true`.

For any run configured with an `llm_*` updater, `llm/input-manifest.json`
fingerprints the external replay corpus before an artifact directory is
created:

```text
{
  schema_version: 1,
  configured_path: string,
  sha256: lowercase 64-character digest,
  response_count: integer,
  models: [model_id, ...]
}
```

This is shape notation, not literal JSON. Reusing an existing run requires
this retained manifest to match the current replay file as well as the run
checksums and source digest.

## LLM request and response

An `LLMRequest` serializes exactly:

```text
{
  schema_version: 1,
  request_id: string,
  updater_id: string,
  view: "response_only" | "full_context" | "provenance_aware",
  system_instruction: string,
  payload: object,
  prompt_sha256: lowercase 64-character digest
}
```

This is shape notation, not literal JSON. `payload` always contains `prior` and
`observation`; full-context and provenance-aware views also contain `context`;
only the provenance-aware view contains `provenance`.

For `LLMReplayUpdater`, `observation` is a model-facing projection that omits
`choice_noise_key`, and `context` omits the audit identifiers `context_id`,
`scenario_id`, and `turn_id`. It also replaces canonical `Option` records with
readable `{option_id, description}` objects and omits numeric `features`,
`target_attribute`, and wording-template IDs. A semantic `profile_schema`
explains the domain-specific meaning of `attribute_1` through `attribute_3`
and their `-2`, `-1`, `+1`, and `+2` levels. Full-context and
provenance-aware requests include the exact assistant/user conversation;
response-only receives the local reply and selected readable option as an
intentional ablation. Its request ID is
`<updater_id>:<prompt_sha256>`, so event IDs that encode experimental
conditions never enter the external envelope.

The prompt hash is computed as:

```text
SHA256(
  UTF8(system_instruction + "\n" + canonical_json(payload))
)
```

For this hash, canonical JSON sorts object keys, uses `,` and `:` without extra
spaces, and preserves non-ASCII text. The hash binds the instruction and
payload. It does not directly hash `request_id`, `updater_id`, `view`, provider,
or model ID.

An `LLMResponse` serializes:

```json
{
  "schema_version": 1,
  "request_id": "request-001",
  "prompt_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "model_id": "provider/model-version",
  "beliefs": {
    "attribute_1": {"-2": 0.1, "-1": 0.2, "+1": 0.3, "+2": 0.4},
    "attribute_2": {"-2": 0.25, "-1": 0.25, "+1": 0.25, "+2": 0.25},
    "attribute_3": {"-2": 0.4, "-1": 0.3, "+1": 0.2, "+2": 0.1}
  },
  "raw_response_sha256": null
}
```

The parser rejects unknown response fields, requires exactly the three
attribute keys and four signed value keys, and checks each row sums to one
within `1e-6`. `ReplayProvider.complete()` requires the requested ID to exist
and the response `prompt_sha256` to match; `validate_coverage()` additionally
enforces an exact request/response ID set when a caller invokes it. No network
call is made.

`raw_response_sha256` is optional in the schema and is emitted as `null` when
unavailable. It is metadata only in v1 because raw provider output is not part
of the response envelope.

### Adaptive request preflight

`llm/request-preflight.json` is a containing v1 run artifact rather than a
standalone exported schema. It records:

- experiment kind, execution mode, calibration mode, and LLM updater IDs;
- experiment, development-calibration, and held-out-paraphrase call
  components;
- logical completion bound, retry factor, physical-attempt bound, configured
  limit, and headroom;
- output tokens per attempt, maximum output allocation, cumulative-token
  limit, and headroom before adaptive input; and
- sensitivity design, point count, and summed trajectory lengths when
  applicable.

`within_declared_retry_expanded_bounds` is true only when the complete
physical-attempt plan and maximum output allocation fit. Adaptive input is
labeled `runtime_enforced_before_each_attempt` because its exact bytes depend
on earlier provider responses. Sensitivity also retains the legacy specialized
`llm/sensitivity-request-preflight.json`; both are derived from the same
validated design.

### Direct OpenAI and OpenRouter provider audits

`openai-provider-audit.schema.json` wraps one provider attempt around its
provider-neutral replay envelope. In addition to request/prompt/body hashes, it
retains requested and returned model labels, response and client/idempotency
IDs, usage, timing, safe raw response metadata, and `acceptance_status`.
`accepted` records may enter replay. `rejected_model_mismatch` records preserve
a charged completed attempt whose model label was missing or inconsistent, but
must not enter `llm/responses.jsonl`.

`openrouter-provider-audit.schema.json` wraps the corresponding OpenRouter
gateway result. It deliberately keeps three identities separate:

```text
gateway/provider:       "openrouter"
requested/returned:     model_requested, model_returned
observed upstream route: upstream_provider, upstream_model
```

The row also requires `routing_strategy`, positive `routing_attempt`, the full
additive `routing_metadata` object, `provider_response_id`,
`provider_created_at`, optional response-header `generation_id`, optional
`cache_status`, raw `usage`, start/completion times, transport-attempt counts,
the conservative token reservation, request/prompt/body/raw-response hashes, a
redacted `raw_response`, and the provider-neutral `replay_response`.
`acceptance_status` is either `accepted` or
`rejected_openrouter_identity`. It also retains the configured
`upstream_provider_constraint`, exact submitted `provider_preferences`,
`route_constraint_evidence`, and
`selected_upstream_identity_semantics`. The selected provider name is a router
display identity, not an exact configured endpoint-slug attestation.

The schema fixes `first_party_origin_claimed` to `false`. A valid row therefore
records what the gateway reported; it does not authenticate the upstream as a
direct first-party source or establish independent errors. Python validation
adds cross-field acceptance checks that JSON Schema alone cannot express:
requested and returned models must match, the strategy must be direct, exactly
one endpoint must be selected, its model must be the canonical requested model
or a conservative dated snapshot of that family, disabled fallback must not
have occurred, cache hits are unusable, and a nonempty material router
pipeline is rejected. Only `accepted` rows may enter `llm/responses.jsonl`.
For selected decoder collection, the complete accepted audits for the exact
`anthropic/claude-sonnet-5` and `google/gemini-3.6-flash` models are additionally
bound to the combined judgments and execution manifest. That collection-level
validation supports `selected_openrouter_gateway_collection`; it does not
change the row-level first-party-origin field.

`llm-provider-transport-attempt.schema.json` is the shared physical-call
journal contract. Its `started` branch binds provider, request/prompt/body
hashes, endpoint, model, client/idempotency identity, conservative reservation,
ordinal, and timestamp. Its `settled` branch records outcome, retry-safety
label, HTTP/response metadata, conservative charge, and the embedded final
OpenAI/OpenRouter audit when one exists. A start without a settlement has an
unknown outcome; a settled request without a final embedded audit is
non-resumable without manual review.

OpenRouter may expose additional router-metadata fields over time, so
`routing_metadata` is retained as an open object even though the enclosing
audit row rejects unknown top-level keys. CAPE-Loop captures generation
identifiers but does not automatically query OpenRouter's separate generation
record endpoint.

### OpenAI suite index

The `llm evaluation-suite` combined index is a containing v1 artifact rather
than a standalone generated schema. It binds the primary/replication source and
resolved config hashes, model/effort declarations, distinct run and journal
paths, per-role ceilings and statuses, output-isolation declaration, and the
limited model-variant/tier replication scope.

## Human-study records

The generated `human-rating` schema covers only the collection result:

```json
{
  "assignment_id": "assignment-001",
  "display_id": "item-0001",
  "rating": 5
}
```

It has no `schema_version`; unknown fields are rejected and `rating` must be an
integer from 1 through 7.

The packet generator separately writes versioned participant items, a
researcher codebook, an order manifest, a copy of the rating schema, and a
checksum-bearing packet manifest. These packet records are not covered by the
generated human-rating schema. Packet generation is not participant
recruitment, consent, deployment, or ethics approval.

The H8 model exchange uses `human-model-evidence.schema.json`. Each versioned
JSONL row names its fitted-aware, ordinary-LLM, or provenance-aware-LLM source;
the independent test-user cluster and matched scenario/condition; the
nonnegative positive-part anchor-directional log-odds update; and the exact
source run, source record, and source-artifact SHA-256. `evaluation_split` is
fixed to `test` and `zero_means_no_evidence` is fixed to `true`.

## H7 volunteered-control records

The direct-statement plan separates model-visible content from withheld
analysis bindings. Each `h7-volunteered-request-binding` joins the provider
request to a deterministic source-user/domain/attribute case, updater role,
view, and content hashes. An accepted provider response becomes
`h7-volunteered-evidence` only after its request, prompt, request body, raw
response, embedded replay record, returned model, and provider audit all
match. The evidence row retains the prior/posterior marginals and the exact
target-direction log-odds update used to construct
`VolunteeredPreferenceUpdate`.

`h7-volunteered-review` is a containing artifact. It binds the verified source
run and plan files, complete response/audit files, paired updates, source H7
component digest, recomputation scope, and self-digest. Cross-record rules such
as exhaustive role coverage, same provider/model within every pair, source-run
immutability, and no imputation are enforced by Python in addition to JSON
Schema.

## Schema evolution

- Regenerate checked-in schemas with
  `PYTHONPATH=src python -m cape_loop schema export schemas`.
- Treat a changed generated-schema `$id` or top-level `schema_version` as the
  compatibility boundary for that record.
- Nested unversioned objects inherit the version of their containing schema or
  experiment artifact.
- Python constructors enforce cross-field constraints that JSON Schema cannot,
  including ranking permutations, displayed-option references, normalized
  probabilities, content-addressed native state IDs, and immutable theta.
- There is no v0-to-v1 migration tool in the current repository. Consumers
  should reject incompatible records rather than reinterpret fields silently.
